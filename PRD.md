# Product Requirements Document — DEVCON Jumpstart Agent Kit

## 1. Summary

The Jumpstart Kit is built **for the DEVCON community**, so members can jumpstart the project they're about to build rather than start from a blank page. It turns a one-line product idea into a set of **development-ready planning documents** — a PRD, a user flow, an architecture decision record, a design system, and optionally a time-boxed MVP scope, runnable starter code, and a demo-day pitch deck — generated inside an existing agent CLI (OpenCode, Claude Code, or Cursor) on free-tier or subscription models.

It exists to remove the "blank page" hour at the start of a DEVCON hackathon, code camp, workshop, or community project: one sentence and one command produce documents a team can actually start building from, not a vague brainstorm.

## 2. Problem statement

DEVCON community members starting a new build — especially under a time limit (hackathons, code camps, workshops, short community sprints) — lose disproportionate time to:

- Writing a PRD from scratch, or skipping it and building on an unclear spec.
- Producing a user flow that's either hand-drawn (slow, inconsistent) or skipped entirely.
- Picking a tech stack without a documented rationale, then re-litigating it mid-build.
- Scoping "what can we actually finish" against real hours and headcount, often too late.
- Reaching demo day with no pitch structure, scrambling to write slides from memory.

Generic "ask an LLM to write a PRD" prompting produces inconsistent structure, hallucinated diagrams, and documents that don't reference each other — the ADR doesn't know what the PRD promised, the design system doesn't know what stack the ADR picked.

## 3. Goals

1. **One command → coherent, cross-referenced docs.** Every downstream artifact reads the upstream one by file path, so the ADR matches the PRD's features and the design system matches the ADR's stack.
2. **Development-ready, not a summary.** Per-feature `Given/When/Then` acceptance criteria, a data model, states/edge cases, and a concrete WCAG 2.2 AA section — output an engineer can build from directly.
3. **Free-tier viable.** Runs reliably on free-tier models (low temperature, minimal tool surfaces, capped retries) — no requirement to pay for a model to use the kit.
4. **Tool-agnostic by construction.** The reusable "brain" (skills, schema, renderer, house rules) is written once and is identical across OpenCode, Claude Code, and Cursor; only a thin per-tool adapter differs.
5. **Deterministic where it matters.** Anything that can be generated by a script instead of an LLM (the flow diagram, starter-code boilerplate) is — removing structural hallucination from the parts most sensitive to it.
6. **Scale to the team's real constraints.** Optional MVP scoping fits the plan to actual hours and headcount rather than the full original vision.

## 4. Non-goals

- Not a replacement for human product judgment — it drafts a first pass an engineer/PM edits, not a final spec.
- Not a code generator beyond a runnable **starter** (hello-world scaffold). It does not build full feature implementations.
- Not tied to any specific LLM vendor or model ID — no model is ever hardcoded.
- Not a project-management or ticketing tool — it produces Markdown/JSON artifacts on disk, not tickets in an external system.

## 5. Target users

The primary audience is **the DEVCON community** — this kit is built for and distributed to DEVCON members to jumpstart the projects they're going to build, not a general-purpose public product.

- **DEVCON hackathon / code-camp participants** who need a working plan and stack decided within the first hour of a fixed time budget.
- **DEVCON workshop facilitators** running multiple teams through the same idea-to-build pipeline.
- **Individual DEVCON members / small community teams** jumpstarting a real side project, chapter initiative, or internal tool from a one-line idea.

## 6. Guiding principle

> **The brain is portable; the wiring is an adapter.**

- `core/` holds all intelligence as vendor-neutral `SKILL.md` skills, a JSON schema, a deterministic Python renderer, and a shared `AGENTS.md` rulebook — written once, identical everywhere.
- `adapters/<tool>/` holds only the per-tool agent/command definitions and provider config. Swapping or adding a tool never touches the brain.
- The full pipeline is also described in one `workflow-orchestration` skill, so a tool without subagents (Cursor) can run the entire thing single-agent; the multi-subagent split (OpenCode, Claude Code) is an optimization, not a requirement.

## 7. Functional requirements (shipped)

| ID | Requirement |
|---|---|
| FR-01 | `/blueprint <idea>` MUST produce `intent.json` → `prd.md` → `flow.json` → `user-flow.md`, in that order, each step reading the prior artifact by file path. |
| FR-02 | `/jumpstart <idea> [hours] [team_size] [skill_level]` MUST run the full pipeline end-to-end: the four `/blueprint` artifacts, plus `adr.md`, `starter/`, `design-system.md`, and `pitch-deck.md`. `starter/` and `pitch-deck.md` MUST always run; `mvp-scope.md` MUST run only when both `hours` and `team_size` are supplied, and MUST be skipped silently (never blocking to ask) otherwise. |
| FR-03 | `/scope <hours> <team_size> [skill_level]` MUST read the latest `prd.md` and write a time-boxed `mvp-scope.md` (protected critical demo path, Build Now / Parked split with effort estimates, per-teammate task breakdown), runnable standalone or as part of `/jumpstart`. |
| FR-04 | `/adr` MUST read the latest `prd.md` (and `mvp-scope.md` if present) and produce `adr.md`: a recommended stack table with alternatives/tradeoffs, system design, and a phased implementation blueprint mapped to the PRD's `FR-xx` feature IDs. |
| FR-05 | `/starter-code` MUST read the latest `adr.md`, extract a structured `stack.json`, and deterministically assemble a real runnable boilerplate under `output/<slug>/starter/` from a fixed template library (React+Vite / Next.js / plain HTML frontend; Node+Express / none backend; JSON-file / Supabase / none database). A stack outside the known templates MUST produce an honest TODO stub, never guessed/hallucinated code. |
| FR-06 | `/design-system` MUST read the latest `prd.md` + `adr.md` (and `mvp-scope.md` if present) and produce `design-system.md`: a UI approach fitted to the product, foundations with real contrast ratios, a component inventory with states, and design tokens aligned to the ADR's frontend stack. |
| FR-07 | `/pitch-deck` MUST read the latest `prd.md` + `adr.md` (and `mvp-scope.md` if present) and produce a 5-slide `pitch-deck.md` with speaker notes (~3 min total), reflecting the scoped MVP if `mvp-scope.md` exists rather than the full original idea. |
| FR-08 | The user flow MUST be produced only by rendering a schema-valid `flow.json` through `render_flow.py` (deterministic Python) — an agent MUST NOT hand-write `user-flow.md`. Invalid graphs MUST fail with a specific, actionable schema error. |
| FR-09 | Every document-authoring step MUST be checked by a read-only validator that returns `PASS` or a concrete `GAPS` list; the author MUST get exactly one retry to close gaps (bounded for free-tier rate limits). |
| FR-10 | Every run MUST write `run.json` listing the path of every artifact produced, and MUST land under a self-contained `output/<slug>/` folder (kebab-case slug of the idea) so runs never overwrite each other. |
| FR-11 | The kit MUST work identically (same commands, same output shape) in OpenCode, Claude Code, and Cursor, via `./scripts/install.sh <tool>` symlinking `core/` and the chosen adapter into the repo root. The installer MUST be idempotent. |
| FR-12 | No agent, command, or config file MAY hardcode a model ID; every agent MUST inherit whichever model the user has selected in their tool. |

## 8. Non-functional requirements

| ID | Requirement |
|---|---|
| NFR-01 | **Reliability on free-tier models** — low temperature (≤0.3) everywhere these are structured tasks, minimal tool surface per agent, capped retries (validator: 1 retry max). |
| NFR-02 | **Least privilege** — the validator agent is read-only; each specialist agent's tool surface is scoped to only what its step needs. |
| NFR-03 | **Determinism where hallucination is costly** — the flow diagram and the starter-code boilerplate are generated by scripts from structured/schema-checked data, not free-form LLM text. |
| NFR-04 | **Portability** — a new capability requires exactly one skill + one agent per adapter + one command per adapter + one pipeline step, with zero changes to existing files (see [`README.md#extending-the-kit`](README.md#extending-the-kit)). |
| NFR-05 | **Consistency across artifacts** — every generated document uses a shared style (YAML metadata header, numbered sections, stable cross-referenced IDs, concrete detail over generic filler; unknowns go to an Open Questions list, never invented). |
| NFR-06 | **Accessibility as a first-class output** — every PRD MUST include a concrete WCAG 2.2 AA section, and every design system MUST state real contrast ratios, not placeholders. |
| NFR-07 | **No network dependency beyond the model provider** — the flow renderer and starter-code generator run fully offline (Python + templates only). |

## 9. Success metrics

- **Time-to-first-doc:** a working `prd.md` + `user-flow.md` within one `/blueprint` call (single command, no manual follow-up prompting).
- **Cross-artifact consistency:** 0 instances of an ADR recommending a stack the design system doesn't reflect, or a PRD feature missing from the ADR's phased blueprint, in a full `/jumpstart` run.
- **Free-tier completion rate:** a full `/jumpstart` run completes without a rate-limit failure on a free OpenRouter/Groq model, given the temperature/retry caps in NFR-01.
- **Tool parity:** identical command surface and output shape across OpenCode, Claude Code, and Cursor for the same idea input.
- **Starter-code honesty:** 0 instances of a generated `starter/` producing a boilerplate that fails to `npm install`/run for a template the stack schema claims to support.

## 10. Current scope (shipped, v2.1)

- Pipeline: `intent.json` → `prd.md` → (`mvp-scope.md`, optional) → `flow.json` → `user-flow.md` → `adr.md` → `starter/` → `design-system.md` → `pitch-deck.md` → `run.json`.
- Commands: `/blueprint`, `/jumpstart`, `/scope`, `/adr`, `/starter-code`, `/design-system`, `/pitch-deck`.
- Adapters: **OpenCode** (multi-subagent + primary orchestrator), **Claude Code** (multi-subagent), **Cursor** (single-agent via `workflow-orchestration`).
- Starter-code templates: React+Vite / Next.js / plain HTML frontend; Node+Express / none backend; JSON-file / Supabase / none database. Anything else produces a TODO stub, not guessed code.
- Full detail on every generated artifact: [`README.md#what-it-produces-expected-output`](README.md#what-it-produces-expected-output).

## 11. Out of scope for this version

- A Codex adapter (`adapters/codex/`) — referenced as a target tool in the original build brief, not yet built.
- Multi-idea / multi-project comparison or portfolio views across `output/` runs.
- Any hosted/SaaS surface — the kit is local-only, run inside an agent CLI against a cloned repo.
- Automated ticket creation (Jira/Linear/GitHub Issues) from the generated PRD.
- Live collaboration or multi-user editing of generated artifacts.

## 12. Roadmap / open items (not yet built)

| Item | Notes |
|---|---|
| **Codex adapter** | The build brief lists Codex alongside OpenCode/Claude Code/Cursor as a target tool; `adapters/codex/` does not exist yet. Adding it needs only a new adapter folder + an `install_codex` case in `scripts/install.sh` per the extension pattern in §13 — no core changes. |
| **Additional starter templates** | `starter-scaffold` currently maps to a fixed template set (react-vite/nextjs/plain-html × node-express/none × json-file/supabase/none); stacks outside this (Vue, Svelte, native mobile, other DBs) fall back to a TODO stub rather than real code. |
| **Pinned/model-selection UX** | Models are fully agnostic today (by design); an optional per-project default-model config (already partially possible via `opencode.json`) could be documented further. |
| **Re-validation after hand-edits** | If a user hand-edits `prd.md` before running `/adr`, there's currently no re-validation step confirming the edited PRD still satisfies the authoring checklist. |

## 13. Extensibility model (how new scope gets added)

- **New capability** (e.g. a test-plan generator): add `core/skills/<name>/SKILL.md`, an agent per adapter, a command per adapter, and one step in `workflow-orchestration` — nothing existing changes.
- **New tool** (e.g. Codex): add `adapters/<tool>/` with that tool's agent/command schema and an `install_<tool>` case in `scripts/install.sh` — the `core/` brain never changes.

Full mechanics: [`README.md#extending-the-kit`](README.md#extending-the-kit).

## 14. Risks

- **Free-tier model drift:** free OpenRouter/Groq model IDs rotate or get rate-limited over time; the kit mitigates this by never hardcoding a model, but a stale user-side selection still surfaces as "model not found" (documented in README Troubleshooting).
- **Schema drift between skill and renderer:** `flow-graph`'s `SKILL.md` and `render_flow.py` / `flow-schema.json` must stay in lockstep; a mismatch fails loudly (`FLOW GRAPH INVALID`) rather than silently, which is the intended fail-safe.
- **Adapter divergence:** because agent/command definitions are duplicated per adapter (OpenCode/Claude Code/Cursor), a change to shared behavior that isn't purely a skill change risks drifting between adapters if not applied to all three.
